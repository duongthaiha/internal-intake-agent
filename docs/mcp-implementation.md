# Intake MCP implementation research

## Status

This document records the recommended design for exposing the intake request
schema and Cosmos DB storage through Model Context Protocol (MCP). It is an
implementation proposal, not a description of functionality currently deployed
by this repository.

## Decision

Build a narrow, intake-specific MCP server rather than exposing generic Cosmos
DB operations or forking the Azure Cosmos DB MCP Toolkit.

The generic toolkit is useful for read-only database exploration, but it does
not provide intake-specific create, update, or submit operations. A custom
server can enforce the intake schema, workflow states, concurrency rules, data
access boundaries, and approval requirements at the domain layer.

Use:

- Python and the official `mcp` SDK, matching the existing agent codebase
- Streamable HTTP at `/mcp`
- A stateless server for the initial implementation
- Azure Container Apps for hosting
- Microsoft Entra ID for inbound authentication
- A managed identity and Cosmos DB data-plane RBAC for data access
- A Foundry Toolbox for connecting the hosted agent to the MCP server
- Azure API Management (APIM) as the production gateway when centralized token
  validation, throttling, versioning, or audit policy is required

## Schema and persistence model

The canonical request payload is defined by
[`schemas/intake-request.schema.json`](../schemas/intake-request.schema.json)
using JSON Schema Draft 2020-12. The current required fields are:

- `title`
- `problemOpportunity`
- `proposedIdea`
- `requester.name`
- `requester.email`

`expectedOutcome` and the discovery and assessment sections are optional.
Unknown properties are rejected.

Every write operation must validate the complete request payload with
`Draft202012Validator` and a format checker so `uuid`, `email`, and `uri`
formats are enforced.

Persist workflow metadata separately from the request payload:

```json
{
  "id": "42f7911f-013d-43f9-9437-4dfe81e05d27",
  "schemaVersion": "1.0.0",
  "status": "draft",
  "createdAt": "2026-08-22T00:00:00Z",
  "updatedAt": "2026-08-22T00:00:00Z",
  "submittedAt": null,
  "createdBy": "<authenticated-principal-id>",
  "idempotency": {
    "key": "<caller-supplied-key>",
    "payloadHash": "<canonical-payload-hash>"
  },
  "request": {
    "title": "Example idea",
    "problemOpportunity": "A sufficiently detailed description of the problem.",
    "proposedIdea": "A sufficiently detailed description of the proposed idea.",
    "requester": {
      "name": "Alex Taylor",
      "email": "alex.taylor@example.com"
    }
  }
}
```

The Cosmos container remains partitioned by `/id`. The MCP server generates the
identifier; callers must not choose database identifiers. The optional `id`
property in schema version 1.0.0 should be treated as server-owned if the
unwrapped schema is used. A future schema version should either formalize the
envelope or remove persistence metadata from the request payload.

## Tool design

Tools should represent business operations rather than database primitives.
Do not expose arbitrary SQL, generic upsert, database discovery, container
discovery, or delete operations.

### Initial tool contract

| Tool | Purpose | Important controls |
|---|---|---|
| `intake_create_draft` | Create a validated draft | Required idempotency key; server-generated ID |
| `intake_get_request` | Read one request by ID | Point read; return ETag; redact unnecessary PII |
| `intake_replace_draft` | Replace the desired draft state | Required ETag; draft-only; validate merged result |
| `intake_submit` | Transition a draft to submitted | Required ETag; completeness check; approval required |

Add these only after reviewer authorization and indexing requirements are
defined:

| Tool | Purpose | Important controls |
|---|---|---|
| `intake_list_requests` | Return bounded request summaries | Projection only; continuation token; maximum 50 |
| `intake_search_requests` | Search selected indexed fields | Parameterized query; bounded results; no raw SQL |

Use MCP resources for passive context such as:

- `intake://schema/v1`
- `intake://guidance/fields`
- `intake://guidance/statuses`

This keeps schema and field guidance discoverable without presenting them as
actions.

## Idempotency

Write tools should be idempotent when the business operation permits it.
Idempotency protects against duplicate model calls, client retries, network
timeouts, and ambiguous responses. It does not make an operation reversible or
safe to run without approval.

### Create draft

Require an `idempotencyKey` generated by the client for the logical operation.
Scope it to the authenticated principal and tool name.

1. Canonicalize and hash the validated payload.
2. Derive or look up the request ID for
   `(principal, tool, idempotencyKey)`.
3. Create the item once.
4. On replay with the same key and payload hash, return the original result.
5. On reuse of the same key with a different payload hash, return a conflict.

Keep the idempotency record in the same logical partition as the request when
atomic behavior is required. Do not implement idempotency as an unprotected
read followed by a create.

### Replace draft

Accept the desired complete draft state rather than commands such as append or
increment. Require the `_etag` returned by the previous read or write and use
Cosmos DB `If-Match` optimistic concurrency. Return a conflict when the ETag is
stale; do not silently fetch and overwrite newer data.

### Submit

Make the state transition idempotent:

- `draft` to `submitted` performs the transition once
- a replay against an already submitted item returns its current submitted
  result
- any incompatible state returns a domain conflict

Submission remains approval-gated because it is an important, effectively
irreversible business action.

## MCP annotations

Annotations communicate risk to clients but do not enforce behavior. The server
must implement the stated guarantees.

| Tool | `readOnlyHint` | `destructiveHint` | `idempotentHint` |
|---|---:|---:|---:|
| Get, list, search | `true` | `false` | `true` |
| Create draft | `false` | `false` | `true` |
| Replace draft | `false` | `false` | `true` |
| Submit | `false` | `true` | `true` |

Treat omitted annotations conservatively. Never mark a tool idempotent merely
because duplicate calls are unlikely.

## Input and output contracts

Each tool needs a restrictive JSON Schema:

- use explicit required fields and enums
- set length and collection limits
- set `additionalProperties: false`
- distinguish omitted values from explicit `null`
- avoid polymorphic `anyOf` or `oneOf` shapes when a simpler schema is possible
- never accept credentials, Cosmos endpoints, database names, container names,
  SQL text, or authorization decisions from the model

Return structured results rather than prose:

```json
{
  "requestId": "42f7911f-013d-43f9-9437-4dfe81e05d27",
  "status": "draft",
  "etag": "\"00000000-0000-0000-0000-000000000000\"",
  "replayed": false,
  "validationErrors": []
}
```

Use stable domain error codes:

- `VALIDATION_FAILED`
- `NOT_FOUND`
- `IDEMPOTENCY_CONFLICT`
- `CONCURRENCY_CONFLICT`
- `INVALID_STATE_TRANSITION`
- `FORBIDDEN`
- `DEPENDENCY_UNAVAILABLE`

Errors should be actionable without exposing stack traces, tokens, database
topology, or request content.

## Authorization

### Foundry to MCP

Register the server as a Foundry remote-tool connection and expose it through a
Foundry Toolbox. Prefer agent identity when each deployed agent needs an
independent security boundary; use project managed identity only when all
agents in the project should share the same permissions.

The MCP Entra application should define application roles:

- `IntakeRequest.Read`
- `IntakeRequest.Write`

Validate the token issuer, audience, expiry, tenant, caller identity, and
`roles` claim on every request. Read tools require the read role. Create,
replace, and submit require the write role.

### MCP to Cosmos DB

Use the Container App managed identity and a custom Cosmos DB data-plane role
scoped to:

```text
/dbs/intake-agent/colls/requests
```

Grant only metadata read, item read, item create, item replace, and bounded
query actions. Exclude item delete, account-wide discovery, stored procedure
execution, conflict management, and key-based authentication.

The current repository grants broader Cosmos contributor access for the hosted
agent's existing history behavior. The MCP server must use its own identity and
narrow assignment rather than inheriting that role.

## Network architecture

Cosmos DB has public access disabled, while the current Foundry managed network
allows internet outbound. The recommended path is:

```text
Foundry hosted agent
  -> public Entra-protected APIM endpoint
  -> internal MCP Container App
  -> Cosmos DB private endpoint
```

Deploy the Container Apps environment into a delegated subnet. Link the
`privatelink.documents.azure.com` private DNS zone to its VNet. APIM provides
the public trust boundary and forwards to the internal Container App through
supported VNet connectivity.

For an initial non-production experiment, a public Container App endpoint can
be used if Entra authentication is mandatory and its outbound path still
reaches Cosmos through the VNet. APIM remains preferred for production rate
limits, policy, versioning, and centralized audit.

## Data protection and prompt-injection controls

- Keep tool descriptions static in source code.
- Validate every write against the canonical schema.
- Return projections from list and search tools, not complete documents.
- Do not include requester email addresses in list results.
- Do not execute instructions found inside stored request text.
- Never call URLs contained in a request.
- Do not log prompts, payloads, emails, names, tokens, or full tool results.
- Cap query sizes, string lengths, page sizes, and execution time.
- Require user approval for `intake_submit`, and consider approval for initial
  creation in high-assurance environments.
- Treat MCP annotations as untrusted hints when consuming third-party servers.

## Observability

Emit OpenTelemetry spans and structured audit events containing:

- tool name
- request ID
- authenticated principal ID
- authorization outcome
- idempotency replay or conflict
- schema validation error count
- ETag match or conflict
- Cosmos request charge
- latency and final status code

Do not capture request content by default. Correlate Foundry, APIM, Container
Apps, and Cosmos telemetry through trace and request IDs.

## Delivery plan

### Phase 1: contract and local server

1. Scaffold a Python MCP server with stateless Streamable HTTP.
2. Package the canonical schema with the server.
3. Implement create, get, replace, and submit.
4. Add schema, idempotency, state-transition, and ETag tests.
5. Add protocol tests using an MCP client.

### Phase 2: private Azure deployment

1. Provision the VNet-integrated Container Apps environment.
2. Add Cosmos private endpoint and private DNS.
3. Assign the narrow custom Cosmos role to the app identity.
4. Configure Entra authentication and app roles.
5. Deploy and test the MCP endpoint.

### Phase 3: Foundry integration

1. Create the Foundry remote-tool connection.
2. Create and publish the Toolbox.
3. Wire `FoundryToolbox` into `create_harness_agent(tools=...)`.
4. Require approval for submission.
5. Test one read and one approved write end to end.

### Phase 4: production hardening

1. Add APIM policies for authentication, rate limits, and version routing.
2. Add list and search only after access rules are defined.
3. Add PII projections and audit retention.
4. Add deployment, contract, integration, and security tests to CI.
